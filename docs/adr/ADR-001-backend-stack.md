# ADR-001: Выбор стека и архитектуры веб-бэкенда

## Статус
Принято

## Контекст
Для реализации REST API (WebLab#3) необходимо выбрать стек серверной разработки. В проекте уже имеется отлаженный модуль бизнес-логики `:domain` на чистом Kotlin (JVM), содержащий сущности и сценарии использования (Use Cases).

## Рассмотренные альтернативы
1. **Go (Gin / Chi):**
   - *Плюсы:* Высокая производительность, низкое потребление памяти.
   - *Минусы:* Необходимость полного переписывания и повторного тестирования бизнес-логики, валидаций и моделей из `:domain`.
2. **Spring Boot (Kotlin / Java):**
   - *Плюсы:* Зрелая экосистема, обилие готовых стартеров.
   - *Минусы:* Избыточный вес и долгое время старта, излишняя сложность для относительно небольшого сервиса.
3. **Kotlin + Ktor Server (Выбранный вариант):**
   - *Плюсы:* Прямое переиспользование модуля `:domain` без дублирования кода, легковесность, асинхронность на корутинах, простая интеграция со Swagger UI и Koin.
   - *Минусы:* Меньше готовых коробочных решений по сравнению со Spring.

## Решение
Использовать **Kotlin + Ktor Server**. Архитектура бэкенда организуется по принципам Clean Architecture с выделением слоев: API (Routing, DTO), Domain (чистая логика) и Data (репозитории).

## Последствия
- 100% переиспользование протестированной бизнес-логики из курса ППО.
- Быстрый запуск и минимальное потребление ресурсов.
