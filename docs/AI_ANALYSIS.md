# Анализ исходного проекта ППО (AI Track Analysis)

Документ содержит результаты декомпозиции и исследования исходной кодовой базы курса ППО (`IU7_7sem_web`) для переноса функционала в веб-систему TimeTracker.

---

## 1. Карта компонентов существующего проекта

```
                                 ┌─────────────────────────┐
                                 │   :app (Android Compose)│
                                 └────────────┬────────────┘
                                              │
┌─────────────────────────┐                   │
│   :tech_ui (Kotlin CLI) │                   ▼
└────────────┬────────────┘        ┌─────────────────────┐
             │                     │ :migration          │
             ├────────────────────►│ DataMigrationUseCase│
             │                     └──────────┬──────────┘
             ▼                                │
┌─────────────────────────┐                   │
│         :domain         │◄──────────────────┤
│ (Models, UseCases, Repo)│                   │
└────────────▲────────────┘                   │
             │                                │
    ┌────────┴────────┐                       │
    │                 │                       │
┌───┴──────────┐   ┌──┴─────────────────┐     │
│    :data     │   │ :data_objectbox    │◄────┘
│ (Room/SQLite)│   │ (ObjectBox NoSQL)  │
└──────────────┘   └────────────────────┘
```

1. **`:domain` (Чистое ядро)**:
   - Бизнес-модели: `TimeRecord`, `Category`, `User`, `DescriptionVersion`, `BusinessConfig`.
   - Репозитории: интерфейсы `IUserRepository`, `ICategoryRepository`, `ITimeRecordRepository`, `IPasswordHasher`.
   - Use Cases: сценарии таймера (`StartTimerUseCase`, `StopTimerUseCase`), ручного добавления (`AddManualRecordUseCase`), категорий (`GetCategoriesUseCase`, `ManageUserCategoryUseCase`, `AdminManageBaseCategoryUseCase`), версий описания (`UpdateRecordDescriptionUseCase`, `RollbackRecordDescriptionUseCase`, `GetDescriptionHistoryUseCase`).
   - *Ограничение:* Чистый Kotlin-модуль без привязки к фреймворкам и платформам.

2. **`:data` (Слой данных Room/SQLite)**:
   - Сущности Room, DAO, мапперы, реализация репозиториев для SQLite с драйвером `BundledSQLiteDriver`.

3. **`:data_objectbox` (Слой данных NoSQL)**:
   - Реализация репозиториев поверх ObjectBox.

4. **`:migration` (Утилита миграции)**:
   - `DataMigrationUseCase` для переноса данных между любыми двумя реализациями репозиториев.

5. **`:tech_ui` (Интерфейс командной строки CLI)**:
   - Консольное приложение на Kotlin JVM с поддержкой сборки в JAR и Dex для запуска на Android через `app_process`.

6. **`:app` (Мобильное приложение)**:
   - Android-приложение на Jetpack Compose с внедрением зависимостей через Koin.

## 2. Подтвержденные факты vs Предположения

| Аспект | Подтвержденный факт (Кодовая база ППО) | Решение для веб-версии |
| :--- | :--- | :--- |
| **Бизнес-логика** | Сценарии таймера, ручной записи, истории описаний и валидаций отлажены в `:domain`. | Модуль `:domain` напрямую подключается к новому модулю веб-сервера без переписывания. |
| **Хранилище** | Использовались SQLite/Room и ObjectBox. | Для серверного бэкенда выбирается реляционная СУБД PostgreSQL. |
| **Сессии** | CLI сохранял текущий UUID в файл `session.txt`. | Web API переводится на токены авторизации (JWT / Bearer). |
| **API** | Сетевое REST API отсутствовало (прямой вызов Use Cases в монолите). | Проектируется контракт OpenAPI 3.1 и Ktor REST API. |

## 3. Разбор противоречий и утвержденные проектные решения

1. **Сессии CLI vs Web API:**
   - *Противоречие:* В TUI авторизация сохранялась локально в файле `session.txt`. Для веб-API необходим защищенный протокол.
   - *Решение:* Web API реализует стандартную Bearer-авторизацию по токенам (JWT), не ломая локальную логику CLI при автономной работе.
2. **Серверная СУБД vs Локальная база:**
   - *Противоречие:* В ППО использовался файловый SQLite, блокирующий параллельные записи в многопользовательском вебе.
   - *Решение:* Для веб-контура вводится PostgreSQL через адаптер репозиториев, сохраняя SQLite/Room для существующих тестов и легаси клиентов.
3. **Версионирование описаний при откате:**
   - *Противоречие:* Удалять ли промежуточные версии при откате описания записи?
   - *Решение:* Откат не удаляет историю, а фиксирует операцию восстановления как новую запись, обеспечивая полный аудит-лог.
