# Лабораторная работа №2: интеграционное и E2E-тестирование

Интеграционные тесты в `web/data/src/test/kotlin/com/ppo/web/it` проверяют совместную работу сценариев `domain` и PostgreSQL-репозиториев. Тест пользовательских сценариев использует тестовый хешер, а не реализацию хеширования backend. Unit-тесты первой лабораторной и новые тесты запускаются раздельными этапами.

E2E-тест `MvpScenarioITCase` отправляет HTTP-запросы в отдельный экземпляр backend и проверяет регистрацию, настройки, категорию, запись времени и её историю. `scripts/run_e2e_scenario.py` воспроизводит сценарий для захвата трафика; `scripts/capture_e2e_traffic.sh` требует запущенный тестовый backend и доступ к tshark или tcpdump. Порт можно узнать командой `docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml port backend-test 8080` и передать как `TARGET_PORT`. Не публикуйте дамп: в нём могут содержаться токены и запросы.

GitHub Actions запускает тестовый контейнер в порядке unit → integration → E2E. Результаты Allure собираются даже при ошибке; не запущенные этапы обозначаются отдельными записями skipped. История сохраняется в кэше между запусками. CI предназначен для self-hosted runner на машине общего стенда; интеграционные тесты подключаются к этому PostgreSQL по loopback. E2E пока выполняется на отдельной временной базе, поскольку не поддерживает транзакционный откат через HTTP.

Общий стенд для интеграционных тестов запускается один раз; каждому разработчику нужен отдельный checkout и отдельное имя Compose-проекта для контейнера тестов:

```sh
docker compose -f deploy/test/docker-compose.shared.yml up -d --wait
export TEST_UID=$(id -u) TEST_GID=$(id -g)
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml build test-runner
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml run --rm test-runner ./gradlew test :web:backend:jar
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml -f deploy/test/docker-compose.shared-runner.yml run --rm test-runner ./gradlew integrationTest
```

Интеграционные тесты запускаются повторно при каждом вызове Gradle. E2E пока использует отдельную временную базу для очистки после сценария; это ограничение описано ниже.

Интеграционные и E2E-тесты обоих стендов прошли дважды; второй прогон выполнялся одновременно с принудительным повторным запуском самих тестовых задач. Это подтверждает проверенный вариант с отдельными рабочими каталогами, но не проверяет работу разработчиков в одном checkout.

Сценарий `run_e2e_scenario.py` выполнен с захватом через TShark на loopback. В проверенном дампе обнаружены все 11 HTTP-запросов и соответствующие 11 ответов, включая удаление записи с кодом 204. Дамп и подробная расшифровка сохранены в `build/reports/traffic/parallel-check-2026-10-27.pcap` и `parallel-check-2026-10-27.log`. В ходе проверки исправлена преждевременная остановка захвата: скрипт ждёт обработки последних пакетов перед завершением TShark.

## Интеграционные тесты на общем стенде

Каждый тест выполняется во внешней транзакции PostgreSQL в общей схеме. Вложенные транзакции Exposed используют savepoint; внешняя транзакция всегда откатывается. Для новых тестов обязательно использовать `TestDbHelper.rollbackRule()`, уникальные идентификаторы и логины, не изменять общие строки и не выполнять работу через другое соединение или переключение потока. Репозитории данного набора работают в том же потоке и соединении; если это изменится, механизм изоляции необходимо пересмотреть. PostgreSQL откатывает незавершённую транзакцию при разрыве соединения; при сетевом разрыве на обнаружение разрыва может потребоваться время.

В тестовой базе уже должны быть таблицы приложения и базовые категории с идентификаторами из `deploy/test/scripts/02_seed.sql`. Тесты не создают и не очищают таблицы стенда. Для двух разработчиков нужны отдельные рабочие каталоги и кэши Gradle, но PostgreSQL должна быть одна. Не запускайте `rollback.sh` против общего стенда: он очищает таблицы целиком.

Локальный общий стенд запускается командой `docker compose -f deploy/test/docker-compose.shared.yml up -d --wait`. Он доступен на `127.0.0.1:55432`, содержит 3 000 синтетических пользователей и 12 000 записей, и сохраняет данные в томе `timetracker-lab2-shared_shared-postgres`. Не выполняйте `down -v` для этого стенда. Локально `./gradlew integrationTest` по умолчанию подключается к нему. Docker-контейнер тестов на той же машине можно подключить через `docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml -f deploy/test/docker-compose.shared-runner.yml run --rm test-runner ./gradlew integrationTest`.

Для GitHub Actions используется self-hosted Linux x64 runner с меткой `timetracker-lab2` на машине стенда. Репозиторий проверяется при push и ручном запуске, а `pull_request` намеренно не запускает код на этой машине. Для стандартных локальных параметров дополнительные GitHub variables не нужны; для иных параметров используются repository variables `POSTGRES_TEST_HOST`, `POSTGRES_TEST_PORT`, `POSTGRES_TEST_DB`, `POSTGRES_TEST_USER` и secret `POSTGRES_TEST_PASSWORD`. Локальная loopback-адресация недоступна для стандартного GitHub-hosted runner.

Официальный runner зарегистрирован в репозитории как `timetracker-lab2-dafuu` и запущен пользовательской службой `timetracker-lab2-runner.service`; его файлы и учётные данные находятся в игнорируемом каталоге `.local/actions-runner`. Runner имеет доступ к машине и Docker; GitHub не рекомендует self-hosted runner для публичных репозиториев, в которых недоверенные пользователи могут влиять на запускаемый код. Репозиторий публичный, workflow не запускается по pull request. Не давайте недоверенным пользователям право push: выполняемый ими код получил бы доступ к машине runner и Docker.

## Проверка изоляции и отката

На постоянном локальном PostgreSQL с 3 000 заранее созданных пользователей и 12 000 записей четыре независимых процесса одновременно успешно выполнили интеграционные тесты; каждый запуск включал проверку отката. Количество строк и контрольные суммы содержимого всех пяти таблиц до и после совпали. Отдельный тест отката проверяет успешный и упавший сценарии и видимость незакоммиченной записи из другого соединения. При принудительном завершении контейнера во время записи существующей строки и добавления пользователя PostgreSQL откатил изменения; контрольные суммы также совпали. Проверка не моделирует нагрузку или объём в терабайт.

E2E-тест взаимодействует с отдельным backend и использует независимую временную базу CI: он создаёт пользователей и категории и не откатывает их в общей базе. Общий стенд для E2E пока не поддерживает гарантию неизменности данных.

## Allure в GitHub Actions

Каждый запуск добавляет в Job Summary счётчики, ошибки и ссылку на полный HTML-отчёт на машине runner. Пользовательская служба `timetracker-lab2-allure.service` слушает только `127.0.0.1:18765`; ссылки доступны в браузере на этой машине, для каждого запуска сохраняется отдельная папка. Отчёт также сохраняется как артефакт GitHub Actions.

После изменения видимости репозитория на публичную GitHub Pages настроен для публикации по адресу https://da-fuu.github.io/IU7_7sem_Web/. Публикуется последний отчёт ветки `tests_02` или основной ветки; доступ разрешён всем. Статический отчёт может содержать данные тестов, поэтому нельзя включать в него секреты или персональные данные.

## Локальная проверка последовательности CI

На машине стенда выполнена последовательность контейнеров unit → integration → E2E → Allure: все три тестовых этапа и генерация HTML завершились успешно. Интеграционный этап использовал постоянный общий PostgreSQL; E2E использовал отдельную временную базу, удалённую после прогона. Пробная генерация отчёта для отказа предыдущего этапа показала два статуса `skipped` для незапущенных этапов. Проверка изменённого workflow в GitHub остаётся до размещения изменений в удалённой ветке; runner зарегистрирован и доступен.
