# Лабораторная работа №2: интеграционное и E2E-тестирование

Интеграционные тесты в `web/data/src/test/kotlin/com/ppo/web/it` проверяют совместную работу сценариев `domain` и PostgreSQL-репозиториев. Тест пользовательских сценариев использует тестовый хешер, а не реализацию хеширования backend. Unit-тесты первой лабораторной и новые тесты запускаются раздельными этапами.

E2E-тест `MvpScenarioITCase` отправляет HTTP-запросы в отдельный экземпляр backend и проверяет регистрацию, настройки, категорию, запись времени и её историю. `scripts/run_e2e_scenario.py` воспроизводит сценарий для захвата трафика; `scripts/capture_e2e_traffic.sh` требует запущенный тестовый backend и доступ к tshark или tcpdump. Порт можно узнать командой `docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml port backend-test 8080` и передать как `TARGET_PORT`. Не публикуйте дамп: в нём могут содержаться токены и запросы.

GitHub Actions запускает тестовый контейнер в порядке unit → integration → E2E. Результаты Allure собираются даже при ошибке; не запущенные этапы обозначаются отдельными записями skipped. История сохраняется в кэше между запусками. Compose создаёт отдельный экземпляр PostgreSQL с начальной схемой и данными; `down -v` удаляет его после выполнения, включая ошибку. При принудительном завершении CI очистку может потребоваться выполнить вручную.

Для локальной изоляции указывайте разное имя проекта для каждого запуска и отдельный checkout: контейнеры используют исходники и каталоги сборки через bind mount. Перед запуском задайте `export TEST_UID=$(id -u) TEST_GID=$(id -g)`. Например:

```sh
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml build test-runner
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml run --rm test-runner ./gradlew test :web:backend:jar
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml run --rm test-runner ./gradlew integrationTest
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml up -d --build backend-test
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml run --rm test-runner ./gradlew e2eTest
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml down -v --remove-orphans
```

После запуска backend необходимо дождаться готовности `/health`, как это делает CI. Для повторного запуска интеграционных тестов используйте `--rerun-tasks`; для первоначального состояния базы удалите стенд и создайте заново. Запуск GitHub Actions подтверждён отдельным прогоном; результаты общего стенда приведены ниже.

## Параллельный запуск и захват трафика

27 октября 2026 года два независимых checkout запустили одновременно два Compose-проекта с отдельными PostgreSQL, сетями, портами и кэшами Gradle. Интеграционные и E2E-тесты обоих стендов прошли дважды; второй прогон выполнялся одновременно с принудительным повторным запуском самих тестовых задач. Это подтверждает проверенный вариант с отдельными рабочими каталогами, но не проверяет работу разработчиков в одном checkout.

Сценарий `run_e2e_scenario.py` выполнен с захватом через TShark на loopback. В проверенном дампе обнаружены все 11 HTTP-запросов и соответствующие 11 ответов, включая удаление записи с кодом 204. Дамп и подробная расшифровка сохранены в `build/reports/traffic/parallel-check-2026-10-27.pcap` и `parallel-check-2026-10-27.log`. Они содержат данные тестового сеанса и не предназначены для публикации. В ходе проверки исправлена преждевременная остановка захвата: скрипт ждёт обработки последних пакетов перед завершением TShark.

## Одновременная работа на общем стенде

При проверке двух рабочих копий на одной PostgreSQL и одном backend исходные интеграционные тесты обоих разработчиков упали: в каждом прогоне 5 из 8 тестов завершились ошибкой из-за очистки общих таблиц. Тестовый помощник изменён: каждый JVM-процесс создаёт собственную PostgreSQL-схему, использует её для создания таблиц и удаления данных, а при обычном завершении закрывает соединения и удаляет схему. Пользователю PostgreSQL требуется право `CREATE` на тестовую базу.

После изменения оба интеграционных прогона одновременно прошли на одном сервере БД; затем два E2E-прогона прошли на одном backend. Дополнительно одновременно запущены интеграционный и E2E-прогоны: оба прошли, ранее созданные E2E-пользователи сохранились, временные схемы отсутствовали. Рабочие копии и кэши Gradle были раздельными.

E2E создаёт уникального пользователя, но после сценария не удаляет пользователя и категорию из общей базы. При аварийном завершении процесса без выполнения shutdown hook временная схема может остаться; при разрыве соединения её удаление также не гарантировано. На общем стенде нельзя выполнять `rollback.sh` или `docker compose down -v`, пока другие разработчики им пользуются: эти операции затрагивают общий экземпляр. Полный откат E2E-данных при аварии на общем стенде отдельно не подтверждён.
