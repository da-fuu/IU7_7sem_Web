# Лабораторная работа №2: интеграционное и E2E-тестирование

Интеграционные тесты в `web/data/src/test/kotlin/com/ppo/web/it` проверяют совместную работу сценариев `domain` и PostgreSQL-репозиториев. Тест пользовательских сценариев использует тестовый хешер, а не реализацию хеширования backend. Unit-тесты первой лабораторной и новые тесты запускаются раздельными этапами.

E2E-тест `MvpScenarioITCase` отправляет HTTP-запросы в общий экземпляр backend и проверяет регистрацию, настройки, категорию, запись времени и её историю. `scripts/run_e2e_scenario.py` воспроизводит сценарий для захвата трафика; `scripts/capture_e2e_traffic.sh` требует запущенный тестовый backend и доступ к tshark или tcpdump. Общий backend доступен локально на порту 18081. Не публикуйте дамп: в нём могут содержаться токены и запросы.

GitHub Actions запускает тестовый контейнер в порядке unit → integration → E2E. Результаты Allure собираются даже при ошибке; не запущенные этапы обозначаются отдельными записями skipped. История сохраняется в кэше между запусками. CI предназначен для self-hosted runner на машине общего стенда; интеграционные тесты подключаются к этому PostgreSQL по loopback. E2E выполняется на том же backend и в той же базе; его данные очищаются по принадлежности прогону.

Общий стенд для интеграционных тестов запускается один раз; каждому разработчику нужен отдельный checkout и отдельное имя Compose-проекта для контейнера тестов:

```sh
./gradlew :web:backend:jar
docker compose -f deploy/test/docker-compose.shared.yml up -d --build --wait
export TEST_UID=$(id -u) TEST_GID=$(id -g)
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml build test-runner
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml run --rm test-runner ./gradlew test :web:backend:jar
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml -f deploy/test/docker-compose.shared-runner.yml run --rm test-runner ./gradlew integrationTest
docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml -f deploy/test/docker-compose.shared-runner.yml run --rm test-runner python3 deploy/test/scripts/e2e_control.py run -- ./gradlew e2eTest
```

Интеграционные и E2E-тесты запускаются повторно при каждом вызове Gradle. E2E следует запускать через `e2e_control.py`: он регистрирует прогон и обеспечивает очистку.

## Интеграционные тесты на общем стенде

Каждый тест выполняется во внешней транзакции PostgreSQL в общей схеме. Вложенные транзакции Exposed используют savepoint; внешняя транзакция всегда откатывается. Для новых тестов обязательно использовать `TestDbHelper.rollbackRule()`, уникальные идентификаторы и логины, не изменять общие строки и не выполнять работу через другое соединение или переключение потока. Репозитории данного набора работают в том же потоке и соединении; если это изменится, механизм изоляции необходимо пересмотреть. PostgreSQL откатывает незавершённую транзакцию при разрыве соединения; при сетевом разрыве на обнаружение разрыва может потребоваться время.

В тестовой базе уже должны быть таблицы приложения и базовые категории с идентификаторами из `deploy/test/scripts/02_seed.sql`. Тесты не создают и не очищают таблицы стенда. Для двух разработчиков нужны отдельные рабочие каталоги и кэши Gradle, но PostgreSQL должна быть одна. Не запускайте `rollback.sh` против общего стенда: он очищает таблицы целиком.

Локальный общий стенд запускается командой `docker compose -f deploy/test/docker-compose.shared.yml up -d --wait`. Он доступен на `127.0.0.1:55432`, содержит 3 000 синтетических пользователей и 12 000 записей, и сохраняет данные в томе `timetracker-lab2-shared_shared-postgres`. Не выполняйте `down -v` для этого стенда. Локально `./gradlew integrationTest` по умолчанию подключается к нему. Docker-контейнер тестов на той же машине можно подключить через `docker compose -p lab2-alice -f deploy/test/docker-compose.test.yml -f deploy/test/docker-compose.shared-runner.yml run --rm test-runner ./gradlew integrationTest`.

Для GitHub Actions используется self-hosted Linux x64 runner с меткой `timetracker-lab2` на машине стенда. Репозиторий проверяется при push и ручном запуске, а `pull_request` намеренно не запускает код на этой машине. Для стандартных локальных параметров дополнительные GitHub variables не нужны; для иных параметров используются repository variables `POSTGRES_TEST_HOST`, `POSTGRES_TEST_PORT`, `POSTGRES_TEST_DB`, `POSTGRES_TEST_USER` и secret `POSTGRES_TEST_PASSWORD`. Локальная loopback-адресация недоступна для стандартного GitHub-hosted runner.

Официальный runner зарегистрирован в репозитории как `timetracker-lab2-dafuu` и запущен пользовательской службой `timetracker-lab2-runner.service`; его файлы и учётные данные находятся в игнорируемом каталоге `.local/actions-runner`. Runner имеет доступ к машине и Docker; GitHub не рекомендует self-hosted runner для публичных репозиториев, в которых недоверенные пользователи могут влиять на запускаемый код. Репозиторий публичный, workflow не запускается по pull request. Не давайте недоверенным пользователям право push: выполняемый ими код получил бы доступ к машине runner и Docker.

Проверка не моделирует нагрузку или объём в терабайт.

## E2E в общей базе и очистка

E2E использует общий backend на `127.0.0.1:18081` и те же таблицы PostgreSQL. Каждый прогон получает случайный идентификатор и удерживает отдельное соединение с advisory lock. При регистрации пользователя триггер атомарно записывает его идентификатор в служебные таблицы `lab2_test.e2e_runs` и `lab2_test.e2e_users`; имена `lab2e2e_<идентификатор>_<номер>` зарезервированы для тестов. Уборщик работает отдельным контейнером на стенде и каждые две секунды проверяет владельцев. После завершения или обрыва соединения он удаляет только связанные с прогоном записи; каскадные внешние ключи очищают настройки, категории, записи и историю. Блокировка между регистрацией и очисткой защищает от запоздавшего запроса. Перед запуском координатор проверяет наличие соединённого уборщика.

E2E записывает данные с обычными коммитами, поэтому они видимы в общей базе, пока прогон работает; это не транзакционная изоляция. После аварии очистка происходит после обнаружения разрыва соединения; при недоступности PostgreSQL или уборщика она возобновится после восстановления. Периодический фоновый автостоп в общем тестовом backend отключён, чтобы он не менял чужие исходные записи; проверки автоостановки выполняются интеграционными тестами. Повторная сборка backend или изменение служебной схемы во время чужих прогонов может им помешать и должна проводиться отдельно.

Четыре E2E-прогона успешно работали одновременно. При принудительном завершении одного из двух работающих контейнеров уборщик удалил его пользователя, категорию и запись, сохранив данные второго. После всех прогонов количество строк и контрольные суммы пяти таблиц совпали с исходными, служебные таблицы были пусты. Дополнительная проверка воспроизводит гонку между регистрацией и очисткой. В тесте на настоящем стенде принудительное завершение контейнера проверено; полный сбой машины и длительный сетевой разрыв отдельно не моделировались.

На уже созданном до этой версии стенде служебную схему нужно установить один раз: `docker compose -f deploy/test/docker-compose.shared.yml exec -T postgres psql -v ON_ERROR_STOP=1 -U timetracker_test -d timetracker_test -f - < deploy/test/scripts/04_e2e_control.sql`, затем собрать и запустить `backend` и `cleanup` из общего Compose-файла. На новом томе SQL применяется при инициализации автоматически.

Отчёт также сохраняется как артефакт GitHub Actions.

После изменения видимости репозитория на публичную GitHub Pages настроен для публикации по адресу https://da-fuu.github.io/IU7_7sem_Web/. ## Локальные отчёты с историей запусков

Для локального запуска с автоматическим отчётом используется `python3 scripts/run_tests.py`. По умолчанию выполняется последовательность unit → integration → E2E; также можно указать один набор: `python3 scripts/run_tests.py unit`, `python3 scripts/run_tests.py integration`, `python3 scripts/run_tests.py e2e`. После ошибки следующая стадия пропускается, отчёт формируется, команда сохраняет ненулевой код завершения.

Результаты каждого запуска сохраняются отдельно в `build/reports/local/<клиент>/<набор>/runs/`, свежий HTML — в `build/reports/local/<клиент>/<набор>/report/`. При генерации подхватывается `history` предыдущего отчёта, а `executor.json` получает возрастающий номер запуска. Панель трендов показывает историю одного клиента и одного набора; локальные запуски не смешиваются с историей CI. Для накопления истории нельзя удалять весь каталог соответствующего клиента/набора.

На машине стенда отчёты доступны через уже работающий HTTP-сервер: `http://127.0.0.1:18765/local-e2e/`, `http://127.0.0.1:18765/local-integration/`, `http://127.0.0.1:18765/local-unit/`, `http://127.0.0.1:18765/local-all/`. Адрес появляется после первого запуска соответствующего набора. При `--client alice` адрес имеет вид `http://127.0.0.1:18765/local-alice-e2e/`. Достаточно обновить страницу после завершения следующего запуска.

Если PostgreSQL недоступен до старта JUnit, обёртка E2E создаёт Allure-результат `E2E: shared database and run cleanup` со статусом `broken` и причиной подключения. Ошибка инфраструктуры отображается жёлтым; нарушение проверки теста — `failed`, красным. Такой результат подтверждает отказ подготовки/очистки E2E, а не выполнение HTTP-сценария.

`scripts/run_parallel_tests.py` использует тот же механизм. История сохраняется отдельно для `dev1`…`devN` между запусками, хотя рабочие копии создаются заново; ссылки и результаты каждого клиента выводятся с префиксом его имени.

Старые команды `./gradlew allureReport` и `./gradlew allureServe` читают `build/allure-results`; они не показывают результаты нового локального запуска, который пишет в отдельный каталог. GitHub Pages показывает последний опубликованный отчёт CI; локальные команды его не обновляют. Сохранённые отчёты CI доступны по адресу `http://127.0.0.1:18765/<run_id>-<attempt>/` и в артефактах Actions.

В текущем CI отдельный шаг `Verify E2E cleanup isolation` удалён: механизм очистки можно проверить вручную командой `python3 deploy/test/scripts/test_e2e_control.py`. E2E-сценарий по-прежнему запускается через координатор для регистрации и очистки своих данных.
