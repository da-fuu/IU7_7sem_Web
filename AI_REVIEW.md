## WebLab#1 — I'm a startuper (and/or a system architect)

- **Задача**: Провести комплексный системный анализ проекта TimeTracker, сформировать технические и архитектурные требования для Web-версии, подготовить Use-Case, BPMN, ER, C4 диаграммы, эскизы интерфейса, оформить ADR и подготовить контекст агента ([AGENTS.md](AGENTS.md)).
- **Инструмент / Модель**: Antigravity Coding Agent (Gemini 3.8 Flash High).
- **Результаты и артефакты**:
  - Комплект системного анализа и спецификация: [README.md](README.md)
  - Контекст и руководство для агентов: [AGENTS.md](AGENTS.md)
  - Исходники диаграмм C4, BPMN, ER, Use-Case: каталог [docs/](docs/)
  - Архитектурные решения: [ADR-001](docs/adr/ADR-001-backend-stack.md), [ADR-002](docs/adr/ADR-002-database.md), [ADR-003](docs/adr/ADR-003-frontend-stack.md)
- **Способ проверки**:
  - Проверка согласованности ролей (`USER`, `ADMIN`), сущностей (`User`, `Category`, `TimeRecord`, `DescriptionVersion`), бизнес-правил (минимальная длительность 1 мин, запрет пересечения интервалов) между Use-Case, BPMN, ER, C4 и эскизами экранов.
  - Проверка валидности синтаксиса PlantUML, DBML и Mermaid диаграмм.
- **Существенные принятые решения**:
  1. *Принято*: Переиспользование ядра `:domain` (чистый Kotlin) в веб-бэкенде на Ktor с сохранением архитектуры Clean Architecture и обеспечением независимости от СУБД.
  2. *Принято*: Использование PostgreSQL в качестве основной СУБД для web-контура с целевой поддержкой primary-replica репликации в Docker Compose для WebLab#5.
  3. *Принято*: Разработка веб-клиента в виде SPA на TypeScript + React + Vite с компонентной архитектурой и строгой типизацией на базе генерируемого из OpenAPI клиента (для WebLab#8).
- **Существенные отклоненные решения**:
  1. *Отклонено*: Переписывание бэкенда на Go или Python. Причина: приведет к дублированию валидации и бизнес-правил, уже реализованных и протестированных в модуле `:domain`.
  2. *Отклонено*: Использование встроенной SQLite для высоконагруженного web-сервера с балансировкой на чтение/запись. Причина: SQLite блокирует файл базы при записи и не подходит для масштабирования в Docker с раздельными репликами (WebLab#5).

## WebLab#2 — REST API System Analyst & OpenAPI 3.1

- **Задача**: Спроектировать контракт REST API по стандарту OpenAPI 3.1.0 для системы TimeTracker, реализовать полный CRUD сущностей, частичное обновление (PATCH), управление таймером в 1 клик, аудит и откат версий описания, сформировать трассировочные таблицы к пользовательским сценариям, подготовить автоматизированную валидацию, mock-сервер и сквозные тесты с фиксацией управления изменениями (Change Management).
- **Инструмент / Модель**: Antigravity Coding Agent (Gemini 3.8 Flash High).
- **Результаты и артефакты**:
  - Контракт OpenAPI 3.1: [web/api/openapi.yaml](web/api/openapi.yaml)
  - Документация и анализ контракта: [web/api/README.md](web/api/README.md)
  - Мок-сервер REST API: [web/api/scripts/mock_server.py](web/api/scripts/mock_server.py)
  - Сквозной тест пользовательских сценариев (15 шагов): [web/api/scripts/test_scenario.py](web/api/scripts/test_scenario.py)
- **Способ проверки**:
  - Индустриальный линтинг схемы через **Redocly CLI** (`docker run --rm -v $(pwd):/spec -w /spec redocly/cli lint web/api/openapi.yaml`): валидация синтаксиса OpenAPI 3.1.0, структурных правил и безопасности (0 ошибок, 0 предупреждений).
  - Валидация через **openapi-spec-validator** (`openapi-spec-validator web/api/openapi.yaml`): полное соответствие официальной спецификации OpenAPI 3.1 (статус OK).
  - Запуск mock-сервера и сценарного теста `python3 web/api/scripts/test_scenario.py`: успешное выполнение 15/15 шагов, включая CRUD категорий, запуск/остановку таймера, проверку конфликта одновременных сессий (`409 Conflict`), ручное создание записей, частичное обновление (`PATCH`), аудит истории и forward-only откат, а также отсечение сессий длительностью менее 1 минуты со статусом `200 OK` (`StopTimerResponse`: `status=DISCARDED`) и валидацию некорректных интервалов (`422 Unprocessable Entity`).
- **Существенные принятые решения**:
  1. *Принято*: Разделение кодов ответа и ошибок в соответствии с семантикой RFC 9110: синтаксис/формат $\rightarrow$ `400 Bad Request`, конфликт состояния (дубликат таймера, коллизия интервалов) $\rightarrow$ `409 Conflict`, семантическая невалидность передаваемого тела запроса (ручное добавление с интервалом $< 1$ мин или $T_{end} \le T_{start}$) $\rightarrow$ `422 Unprocessable Entity`. Для команды остановки таймера (`POST /timer/stop`) при длительности менее 1 минуты возвращается статус `200 OK` со статусом `DISCARDED` (`StopTimerResponse`) вместо 422, так как клиент не передает невалидного тела и запрос успешно выполнен сервером.
  2. *Принято*: Реализация частичного обновления сущностей через HTTP `PATCH` с семантикой JSON Merge Patch (RFC 7396) для гибкого обновления описания или категории записи без перезаписи всех полей.
  3. *Принято*: Forward-only аудит версий описания (`POST /records/{id}/history/{versionId}/rollback`): откат восстанавливает состояние, предварительно архивируя текущий текст в историю, что исключает деструктивную потерю данных.
  4. *Принято*: Единый машиночитаемый формат ошибок (`ErrorResponse`: `code`, `message`, `details`, `timestamp`), совместимый с рекомендациями RFC 7807 Problem Details.
- **Существенные отклоненные решения**:
  1. *Отклонено*: Реализация GraphQL (Bonus #1) или RPC-эндпоинтов. Причина: строгое ограничение проекта CORE PROGRAM ONLY (NO BONUSES); стандарт REST + OpenAPI 3.1 полностью покрывает требования системы.
  2. *Отклонено*: Автогенерация OpenAPI контракта из кода бэкенда (Code-First). Причина: принцип CONTRACT FIRST — контракт является независимым источником истины для параллельной разработки бэкенда (Ktor, WebLab#3) и фронтенда (React SPA, WebLab#8).
  3. *Отклонено*: WebSocket для таймера на этапе проектирования базового API. Причина: таймер рассчитывается детерминированно по разнице текущего серверного времени и `startTime`, поэтому REST-эндпоинта `GET /api/v1/timer/active` и локального отсчета на клиенте достаточно без накладных расходов на постоянное WS-соединение.
  4. *Отклонено*: Возврат ошибки 422 Unprocessable Entity при остановке таймера короче 1 минуты. Причина: согласно RFC 9110, класс 4xx указывает на ошибку в запросе клиента, требующую модификации для повторной отправки. При остановке таймера клиент не передает ошибочных данных, а отправляет команду фиксации завершения сессии. Запрос легитимен и успешно обработан бизнес-логикой, поэтому возвращается 200 OK с детерминированным статусом результата (SAVED или DISCARDED).
